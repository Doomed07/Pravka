# Правки (рабочее название): ассистент юриста по правкам контрагента

Читать первым. Продукт: программа разбирает правки контрагента в договоре (docx), сравнивает версии по раундам,
классифицирует правки и по плейбуку компании подсказывает: принять, уступить, отклонить или «решает юрист».
Для российских компаний. Владелец продукта — юрист; общение с ним на русском.

## Принципы, которые нельзя ломать
1. **Решения принимает детерминированный слой** (разбор docx, сравнение, правила плейбука). Модель только объясняет, и её
   ответ проходит защиту (числа и ссылки на статьи должны быть в фактах и плейбуке).
2. **Сомнение уходит юристу.** «Принять» только после проверки по правилу. Ложное «принять» — самая опасная ошибка.
3. **Сторона договора определяется и проверяется** (`pravki/parties.py`): плейбук привязан к роли, при несовпадении или
   неопределённости разбор не запускается (код выхода 3). Стороны сверяются в каждом раунде.
4. **Конфиденциальность.** Договоры, плейбуки, профиль компании, журналы проектов в репозиторий не попадают
   (см. `.gitignore`). Данные не уходят в облачные модели; адрес модели по умолчанию только локальный (152-ФЗ).
5. **Каждый выходной файл заканчивается** «Черновик — требует вашей проверки перед отправкой (draft — needs your review
   before sending)». Продукт не выдаёт окончательных формулировок для внешнего использования.
6. Порядок в отчёте: изменение сторон и реквизитов, затем возмещение убытков, ограничение ответственности, расторжение.
7. **Обезличивание.** В облачную сессию попадают только обезличенные файлы и выдержки. Карту замен
   (`anon_map.json`, `anon_map.index.json`) и список исходных файлов не печатать и не отправлять: в них настоящие данные.

## Команды
    pip install -r requirements.txt          # Python 3.10+
    python -m pytest -q                      # все тесты, в том числе зеркальный
    python -m pravki synth demo              # учебная пара договоров
    python -m pravki review demo/theirs_tracked.docx --base demo/base.docx \
        --playbook playbooks/services_example.yaml --our-inn 7701234567 --out demo/out
    python -m pravki eval                    # метрики на синтетических договорах
    python -m pravki anonymize ... --out data/golden/anon --map data/golden/anon_map.json   # см. README «Золотой набор»
    python -m pravki worksheet --pair "Имя=theirs.docx::base.docx" --out data/golden/anketa.xlsx
    make env-init && make up                 # веб-сервис в Docker (Go + движок на Python), http://127.0.0.1:8080
    go test ./...                            # тесты Go; хранилище — с PRAVKI_TEST_DB=1 и PostgreSQL

## Как вносить изменения
* Работа в ветках `feature/...` или `fix/...`, в `main` через pull request; перед коммитом `python -m pytest -q`.
* Новое правило или логика сопровождается тестом, который падает без неё (проверьте поломкой кода).
* Правки плейбука обеих ролей (`services_example.yaml` и `services_customer_example.yaml`) прогоняйте через
  `tests/test_mirror.py`: одна и та же правка не должна получать «принять» сразу для обеих сторон.
* `context` в проверке `number` ограничивает проверку предложениями с нужными словами; регулярку пишите для всех форм слова.
* Тест не подгоняют под результат: сначала понять, ошибка в правиле, формулировке или движке.
* Коммиты на русском, коротко: что и зачем.

## Устройство
Веб-сервис на Go (каркас из проекта Bookshelf) в `cmd/`, `internal/`, `web/`, `migrations/`; движок на Python — `pravki/`,
связь через `pravki/engine_api.py` ↔ `internal/engine`. Решения по правкам принимает только движок (плейбук).
См. раздел «Устройство» в `README.md`, решения проекта в `docs/DECISIONS.md`, состояние и следующие шаги в `STATUS.md`,
контекст прошлых обсуждений с владельцем — в `docs/HANDOFF.md`.
