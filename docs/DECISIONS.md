Подтверждены владельцем продукта. Менять только осознанно и записывать здесь.

| Тема | Решение |
|---|---|
| Развёртывание | Один пакет в двух режимах: выделенный экземпляр одного клиента в российском облаке и тот же пакет в периметре клиента. Общее облако для многих клиентов — после MVP. |

| Сторона договора | Плейбук = тип договора + наша роль. Роль определяется по преамбуле и подтверждается юристом; при несовпадении или неопределённости анализ блокируется; стороны сверяются в каждом раунде; зеркальный тест на плейбуках обеих ролей. |
| Золотой набор | Обезличенные примеры владельца с разрешения работодателя, открытые образцы, синтетические договоры. |
| Данные | Реальные договоры, плейбуки и профиль компании в репозиторий не кладутся. Хостинг и модели только в РФ или в периметре клиента (152-ФЗ). |
| Бюджет | Почти нулевой; команда: владелец продукта и Claude. |

## Принято в сессии 2026-10-22

| Тема | Решение |
|---|---|
| Обезличивание | Владелец разрешил обезличивать самостоятельно и затем использовать. Обезличивание — на компьютере владельца (`anonymize`), карта замен и список исходных файлов остаются там же; в облачную сессию попадают только копии. |
| Разметка | Юрист размечает анкету (xlsx): тема верна / правильная тема, решение, граница уступки. Программа предзаполняет свои выводы, чтобы юристу оставалось только исправлять. |
| Плейбук из своих правок | Черновик плейбука собирается из правок самого юриста (автор «Мы») в обезличенных договорах, лежит в `playbooks/private/` и проверяется юристом. Роль в договоре обязательна: у работодателя есть и поставка (он Поставщик), и услуги (он Заказчик). |
| Согласие в комментарии | Если контрагент согласился в комментарии («+», «ок», «не возражаю»), условие согласовано и правку можно принимать. Программа помечает такой комментарий «согласие в комментарии»; «ок, но…» и «ок с корректировкой» — «согласие с условием», условие проверяет юрист. |
| Авторы правок | Сторону автора правок не угадываем: кто «наш», а кто контрагент, подтверждает юрист (ошибка 2026-10-22: правки коллеги приняты за правки контрагента). |
| Веб-приложение | Первая версия — на компьютере юриста (`python -m pravki web`, только 127.0.0.1), без внешних библиотек. Общий сервер для команды и облачная модель — отдельное решение (152-ФЗ, конфиденциальность), пока не принято. |
| Веб-сервис (2026-10-22) | Каркас — проект владельца Bookshelf (Go: вход, сессии, PostgreSQL, страницы, метрики), движок «Правки» на Python — отдельный внутренний сервис в той же сети Docker. Запуск: docker compose на Mac или сервере. Исходные договоры не храним, только отчёты; регистрация на сервере — по коду приглашения. Модель для пояснений — локальная (Ollama), в Docker или на Mac. |
| Два агента (идея владельца) | Принята как красная команда и генератор раундов, но не как источник истины: агент-контрагент ищет правки, которые детерминированный слой ошибочно «принимает»; оба агента выдают предложения правок в JSON, docx с рецензированием собирает программа. Расхождения агента-юриста с программой уходят живому юристу. Синтетические раунды проверяют устойчивость и регрессии, точность на них не измеряется. В облако — только обезличенные данные. Не реализовано, ждёт подтверждения. |
| Опечатки и грамматика (2026-10-24) | Написание слов проверяется по словарю русского языка (pymorphy3, локально). Исправленная ошибка и правильная грамматическая правка — «Принять» автоматически; ошибку внёс контрагент («собственность» → «собсвенность») — техническая правка, «Отклонить» без юриста; два разных настоящих слова («предоставить» → «представить») или слова не из словаря (сокращения, названия) — не опечатка, обычным путём. Сомнение модели больше не отменяет решение правила, а пишется заметкой в карточку. |
| Форматы файлов (2026-10-24) | Кроме .docx разбираем .odt (с рецензированием, как docx) и PDF с текстом (pypdf, локально; правки находятся только сравнением с нашей версией, поэтому наша версия для PDF обязательна; сканы не поддерживаются, распознавание текста — отдельный шаг). Формат определяется по содержимому. Word с примечаниями и ответ контрагенту в Word собираются из XML файла контрагента, поэтому только для .docx. Напечатанные номера пунктов (PDF, ручная нумерация) при сравнении с автонумерацией не считаются правками. Правки из текста письма — позже. |
| Контрагенты и папки (2026-10-24) | Порядок работы: на главной загружается первая версия договора (как прислал контрагент, без наших правок); программа находит контрагента по преамбуле (сторона, не совпавшая с нашей компанией), юрист подтверждает или правит; создаются контрагент → договор → раунды. Следующие раунды добавляются на странице договора. Параллельно файлы кладутся в `data/contracts/Контрагент/Договор/Раунд N/`: версия контрагента и наша версия с ответами (при сборке ответа, перезаписывается). Путь договора пишется в базу при создании и не меняется при переименовании контрагента; файлы с сайта не удаляются (удаление — только вручную). Это меняет прежнее решение «исходные договоры не храним»: теперь они лежат на диске владельца вне Git. 6 прежних разборов привязаны к контрагенту «Без контрагента» (переименовывается, договор можно перенести), файлов на диске у них нет. PDF-первая версия: служит и точкой отсчёта (наша версия = она же). |

## Ждём от владельца продукта
* Два плейбука по 15–20 правил (оказание услуг, аренда) вместо учебных примеров.
* Один-два обезличенных docx с рецензированием из реальных переговоров.
* Пороги согласования и категории высокого риска (черновик допустим).
* Замер времени на пять раундов правок и 8–10 интервью (набор в Claude Doc «Интервью с юристами»).
* Проверка, что работодатель разрешает использовать обезличенные примеры.

## Открыто
* Скорость GigaChat 3.1 Lightning (Q4_K_M, около 6,5 ГБ) на MacBook с 16 ГБ не измерена.
* Матрица согласования (по уровню риска или ещё и по сумме).
* Название продукта: рабочее «Правки» (пакет `pravki`).
