# Правки — версия 0

Помощник юриста по правкам контрагента в договоре. Берёт версию, которую отправили вы, и версию контрагента,
находит **все** изменения (в том числе «тихие», без отметки в рецензировании), определяет тему, область
компетенции и существенность, сверяет с вашим плейбуком и выдаёт рекомендацию. Решение всегда за юристом.

Работает локально, без сети и платных сервисов. Модель не нужна: в v0 решения принимают правила плейбука.

## Установка

Python 3.10+.

    pip install -r requirements.txt
    python -m pytest -q          # 60+ тестов, должны пройти

## Быстрый старт на примере

    python -m pravki synth demo --template services          # создаст demo/base.docx и demo/theirs_tracked.docx
    python -m pravki review demo/theirs_tracked.docx --base demo/base.docx \
        --playbook playbooks/services_example.yaml --our-inn 7701234567 --out demo/out

`--our-inn 7701234567` — ИНН «нашей» компании в учебном договоре: по нему программа понимает, что мы Исполнитель
(см. «Какая сторона договора наша»). Откройте `demo/out/report.html` (для чтения), `demo/out/report.xlsx` (для работы)
и `demo/out/unified.docx` — единую версию в Word: правки контрагента на месте, наши решения в примечаниях на полях.

## Веб-сервис в Docker (на Mac или на сервере)

Полноценный сервис с входом по паролю, историей разборов и базой данных. Каркас взят из проекта Bookshelf
(Go, PostgreSQL, страницы на HTML и JS, метрики), разбор выполняет движок «Правки» на Python в соседнем контейнере.

    make env-init      # создать .env со случайными паролями (один раз)
    make up            # собрать и запустить: база, миграции, движок, веб-сервис
    open http://127.0.0.1:8080

* Зарегистрируйтесь на странице «Регистрация». Если в `.env` задан `AUTH_SIGNUP_CODE`, без этого кода
  зарегистрироваться нельзя — на удалённом сервере задайте его обязательно.
* Ваши плейбуки из `playbooks/private/` подключаются к движку только для чтения: правите файл — изменения видны сразу.
* Исходные договоры не сохраняются; в базе (`out/pgdata`) остаются отчёты. Каждый пользователь видит только свои разборы.
* Модель для пояснений — GigaChat 3.1 Lightning (открытые веса, лицензия MIT), её запускает программа Ollama: `make ai-up && make ai-pull`, затем в `.env` `PRAVKI_LLM_URL=http://ollama:11434/v1` и `make up`.
  На Mac Docker не использует видеокарту, поэтому модель в контейнере работает медленно: быстрее поставить Ollama прямо
  на Mac и указать `PRAVKI_LLM_URL=http://host.docker.internal:11434/v1`. Решения по правкам принимает плейбук в любом случае.
* На сервере: тот же `make up`; наружу публикуйте только через обратный прокси с HTTPS (например, Caddy или nginx),
  `AUTH_COOKIE_SECURE=true`, `APP_PORT=127.0.0.1:8080`.
* Устройство: `cmd/pravkiapp` — точка входа; `internal/core` — общие части (вход, сессии, HTTP, метрики);
  `internal/features/auth` — регистрация и вход; `internal/features/reviews` — разборы; `internal/engine` — клиент
  движка; `web/` — страницы; `migrations/` — схема базы; `pravki/engine_api.py` — HTTP-сервис движка.
* Тесты: `go test ./...` (тест хранилища запускается при `PRAVKI_TEST_DB=1` и настоящей PostgreSQL) и `python -m pytest -q`.

## Веб-приложение (проще всего)

Двойной щелчок по файлу `Правки.command` в папке проекта (или `python -m pravki web`): откроется браузер со страницей
«Новый разбор». Загрузите версию контрагента и, если есть, нашу версию, выберите плейбук — получите отчёт на странице и
в Excel. Прошлые отчёты сохраняются в `projects/web/` и видны на главной.

* Сервер работает только на этом компьютере (адрес 127.0.0.1): договоры никуда не отправляются, из сети страница недоступна.
* При первом запуске `Правки.command` сам создаёт окружение и ставит зависимости.
* Пояснения модели («ИИ») включаются переменными `PRAVKI_LLM_URL` и `PRAVKI_LLM_MODEL` (локальная модель, например
  Ollama); решения по правкам всё равно принимает плейбук.

## На реальном договоре

    python -m pravki review ПРИСЛАЛИ.docx --base ОТПРАВИЛИ.docx \
        --playbook мой_плейбук.yaml --company моя_компания.yaml \
        --project проекты/ООО_Ромашка --name "Договор с ООО Ромашка"

* `--base` — файл, который вы отправили. Без него видны только правки в рецензировании, «тихие» правки не найти.
* `--our-author "Иванов И."` — укажите, если в файле есть и ваши отмеченные правки (можно несколько раз).
* `--project` — папка проекта: раунд попадёт в журнал, повторные правки будут помечены.
* Решение по правке: `python -m pravki decide проекты/ООО_Ромашка E007 rejected --note "не согласны"`
  (статусы: `accepted`, `rejected`, `counter`). История: `python -m pravki history проекты/ООО_Ромашка`.

Файл контрагента может быть с рецензированием, «чистым» или с рецензированием и тихими правками одновременно.

## Золотой набор: обезличить и разметить

Качество программы измеряется только на правках, где юрист сказал, как правильно. Путь от настоящих договоров до набора:

    # 1. обезличить договоры одной картой замен (пары версий остаются парами); всё выполняется на вашем компьютере
    python -m pravki anonymize договор1.docx договор2.docx ... --out data/golden/anon --map data/golden/anon_map.json \
        --author "Иванов И.=Мы" --author "Admin=Контрагент" --term "Ромашка=Бренд-1" --residual
    # 2. анкета: правки контрагента → xlsx, где юрист отмечает тему и решение
    python -m pravki worksheet --our-author Мы --out data/golden/anketa.xlsx \
        --pair "Договор А=версия_контрагента.docx::наша_версия.docx" --pair "Договор Б=версия_контрагента.docx"
    # 3. ответы юриста → json (для загрузки в оценку качества)
    python -m pravki labels data/golden/anketa.xlsx --out data/golden/labels.json

* `anonymize` заменяет названия организаций (во всех падежах и написаниях), ФИО и инициалы, ИНН/ОГРН/счета/телефоны,
  адреса и номера домов, почту и сайты, авторов правок и комментариев, свойства файла (автор, компания, шаблон),
  картинки (печати, подписи) и внутренние данные Word. После замены проверяется каждый файл; найденный остаток —
  код выхода 4. `--residual` показывает слова, которые могли остаться (бренды, мероприятия, города): их добавляют
  через `--term`. **Карта замен и список исходных файлов содержат настоящие данные — хранить только у себя.**
* Склонение ФИО не сохраняется: замена идёт той же формой «Фамилия Имя Отчество» независимо от падежа.
* Анкета объединяет шум: «склейки абзацев» одного пункта — одна строка, короткие обрывки одного абзаца — одна.

## Какая сторона договора наша

Одна и та же правка по-разному оценивается для сторон: рост неустойки за просрочку оплаты выгоден Исполнителю и
неприемлем Заказчику. Если программа примет не ту сторону, «принять» и «отклонить» поменяются местами, и это не видно
в отчёте. Поэтому плейбук привязан к роли (`our_role`), а перед разбором программа сверяет её с договором:

1. В начале договора (до первого пункта) находит стороны и их роли: «…, именуемое в дальнейшем «Исполнитель»».
2. По профилю вашей компании (`--company файл.yaml` с ключами `names` и `inn`, либо `--our-name`, `--our-inn`)
   определяет, кто из сторон вы. Совпадение по ИНН или полному наименованию — высокая уверенность, по наименованию без
   формы (ООО/АО) — средняя. Ни одной стороны или обе — «не определено».
3. Не совпало с ролью плейбука или не удалось определить — **разбор не запускается**, отчёт не создаётся, код выхода 3.
   Роль можно подтвердить явно: `--confirm-role Исполнитель`. Подтверждение вопреки преамбуле помечается в отчёте.
   Исполнитель и Подрядчик, Продавец и Поставщик считаются одной стороной; «Сторона 1/2» роль не определяет.
4. В каждом раунде стороны версии контрагента сверяются с нашей версией: смена роли, наименования, ИНН/ОГРН,
   числа сторон попадает в начало отчёта отдельной правкой «стороны и реквизиты» и требует решения юриста.
5. Проект в журнале запоминает роль: смена плейбука на другую роль в том же проекте требует `--confirm-role`.

Ограничения: разбирается только преамбула; реквизиты в конце договора (таблицей) не читаются; ИНН и ОГРН
учитываются, только если они есть в преамбуле; роль можно писать с кавычками и без, иностранные наименования
распознаются по форме (Ltd, LLC, GmbH, AG…). Профиль компании — конфиденциальный файл, в репозиторий его не кладут.

## Единая версия договора

После загрузки двух редакций (нашей отправленной и ответа контрагента) страница разбора показывает один текст договора:

* вставки подчёркнуты, удаления зачёркнуты; правки **без отметки в рецензировании** выделены отдельным цветом
  и подписаны — их нашло сравнение двух редакций (в том числе внутри абзаца, где есть и отмеченные правки);
* слева итог по плейбуку и список правок в порядке отчёта, на полях у каждого пункта — решение, правило,
  пояснение (с пометкой «Пояснение ИИ», если его написала модель) и наша позиция;
* «Скачать Word с примечаниями» — тот же договор в docx: текст и правки контрагента не меняются, к каждой правке добавлено
  примечание Word от автора «Правки (черновик)», в конце — дисклеймер вставкой в рецензировании. Этот автор всегда
  считается нашим: если файл вернётся от контрагента, примечания и дисклеймер не станут «его правками».

Устройство: `pravki/unified.py` (абзацы с правками), `pravki/annotate.py` (docx с примечаниями). У разборов, сделанных
до появления единой версии, страница показывает прежний отчёт.

## Что в отчёте

* Правки в порядке приоритета: сначала возмещение убытков, ограничение ответственности и расторжение,
  затем остальные, технические (опечатки, знаки) свёрнуты.
* Оформление: вставки подчёркнуты, удаления зачёркнуты, комментарии и разбор — на полях.
* Для каждой правки: пункт, источник (в рецензировании / **тихая правка** / найдена сравнением), автор, тема,
  области (юридическая, финансовая, бухгалтерская и налоговая, коммерческая, ИБ), существенность,
  рекомендация, пояснение, позиция по плейбуку, кого согласовать.
* Режим «нужно решение юриста» — когда правила не нашлись, проверка неприменима или есть риск ошибки
  (отрицание, тихая правка, комментарий). «Принять» ставится только после успешной проверки по правилу.
* Сводка для бизнеса: что меняется по деньгам, срокам и обязательствам.
* Каждый выходной файл заканчивается: «Черновик — требует вашей проверки перед отправкой».

## Плейбук

Файл `.yaml`, примеры в `playbooks/`. Правило:

    - id: SV-01
      title: Неустойка за нашу просрочку
      topic: неустойка и штрафы             # тема из классификатора (список в pravki/classify.py)
      match: ['Исполнител\w+\s+уплачива']   # необязательно: регулярные выражения для выбора правила
      preferred: 0,1% в день                # наша позиция (покажется как черновик встречной)
      fallback: до 0,3% в день
      red_line: больше 0,3% в день
      escalate_to: Директор по правовым вопросам
      checks:
        - {type: number, unit: percent, direction: max, preferred: 0.1, fallback: 0.3, context: 'Исполнител|оказани'}

Типы проверок: `number` (значение с единицей: percent, days, months, years, monthly_payments, multiple, money),
`change` (допустимое изменение числа в процентах, например цена), `forbid` (запрещённые формулировки),
`require` (формулировка, которую нельзя удалять), `deletion_redline` (любое удаление — красная линия).
Примеры в `playbooks/` — для отладки, это не юридическая позиция: замените значения своими.

`context` в проверке `number` ограничивает её предложениями, где есть нужные слова. Если таких предложений нет, правило
к правке не применяется (а не проверяет весь абзац), поэтому регулярку `context` нужно писать с учётом всех форм слова
(«оплат|оплач»).

### Плейбуки для двух сторон и зеркальный тест

`playbooks/services_example.yaml` (мы — Исполнитель, правила SV-NN) и `playbooks/services_customer_example.yaml`
(мы — Заказчик, SC-NN) — зеркальные пары: правило SC-NN на той же теме, что SV-NN, там где интересы противоположны.
`tests/test_mirror.py` прогоняет одни и те же правки под обоими плейбуками (39 асимметричных правок, обратные правки,
сдвиги чисел по шкалам, красные линии) и проверяет, что выводы зеркальны и что значительная правка не получает
«принять» сразу для обеих сторон. Правила, которые нельзя выразить имеющимися проверками (взаимный срок отказа от
договора, подсудность, НДС), в плейбуке Заказчика переведены в «решает юрист». Свой плейбук для второй роли
начинайте с зеркальной копии и прогоняйте этот тест на своих правилах.

## Что проверено

| Проверка | Результат |
|---|---|
| Тесты (разбор, сравнение, плейбук, отчёты, журнал, защиты) | проходят |
| Синтетические договоры, 200 пар / 4447 правок: полнота, точность, пункты, темы, уровни | 100% (ошибок нет) |
| Файлы, пересохранённые в LibreOffice (другой «диалект» docx) | результат тот же |
| Тема правки на 24 формулировках вне шаблонов (holdout) | **75%** |
| Скорость: договор на 800 абзацев с массовой переписью | ≈1 с |

Важно: договоры синтетические, их написал тот же автор, что и разбор, а правила тем подгонялись под них.
Цифры в 100% доказывают, что разбор файлов работает и что ничего не ломается, но **не** качество на реальных
договорах. Честная оценка темы вне шаблонов — 75% (4 из 6 ошибок — «прочее» → безопасный отказ к юристу).
Настоящие цифры даст золотой набор из ваших переговоров (10–15 пар, около 300 правок). Загрузка такого набора
в `eval` — следующий шаг (см. STATUS.md); сейчас `eval` считает метрики только на синтетических договорах.

## Ограничения версии 0

* Только docx. .doc, .odt, .ods, Excel, PDF, текст письма — позже.
* Не читаются сноски, колонтитулы, изменения форматирования, структура таблиц (протокол разногласий в таблице — тоже).
* Тема правки определяется ключевыми словами; на нестандартных формулировках выдаёт «прочее» и отправляет к юристу.
* Дни в проверках не различают календарные и рабочие.
* Согласующие, принятие рисков руководителем, предподписная проверка, интеграции — не реализованы.
* Слой модели (`--llm-url`) написан и проверен на заглушке; с реальной GigaChat не запускался.
* Сторона договора определяется по преамбуле; нестандартные формулировки сторон уходят на подтверждение юристу.

## Безопасность

Договоры считаются недоверенными файлами: внешние сущности XML отключены, размер частей ограничен, текст в HTML
экранируется, значения в Excel не превращаются в формулы. Данные никуда не отправляются; адрес модели по умолчанию
только локальный (152-ФЗ: персональные данные и коммерческая тайна).

## Разработка

Python 3.10+. Ветки `feature/...` и `fix/...`, в `main` через pull request, на GitHub тесты запускаются сами
(`.github/workflows/tests.yml`). Правила для тех, кто пишет код, и принципы продукта — в `CLAUDE.md`, решения — в
`docs/DECISIONS.md`. Реальные договоры, плейбуки и профиль компании в репозиторий не кладут.
